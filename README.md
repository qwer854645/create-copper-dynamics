# Create: Copper Dynamics — CCD

机械动力：铜流工程。当前版本：`0.3.0-alpha.1`。

这是首个流体打包原型：继承 Create 的包裹和打包机类，流体直接保存于包裹的数据组件中。
同一个流体打包机从背后的流体容器打包，也将收到的包裹拆进背后的流体容器。

## 运行环境

- Minecraft 1.21.1、Java 21。
- NeoForge 21.1.219 或更新的 21.1 系列；本次验证版本为 21.1.219。
- Create 6.0.10；本次构建针对 Maven `6.0.10-280`。
- 不声明兼容 Create 6.0.11，待对应版本验证后再开放范围。
- 开发运行依赖 Ponder 1.0.82、Flywheel 1.0.6、Registrate MC1.21-1.3.0+67；普通玩家使用正常安装的 Create 及其所需依赖。
- 模组同时安装在服务端和客户端。

## 如何使用

1. 在创造模式的“机械动力：铜流工程”物品栏取得“流体打包机”。生存配方为一列：铜锭、Create 打包机、Create 流体储罐。
2. 将流体打包机贴在储罐上。背面连接容器，正面负责包裹收发；支持六个方向。必要时用扳手调整朝向。
3. 用管道向背后的储罐供液。机器不需要旋转动力，也没有可供管道访问的内部储罐。
4. 红石触发封装；持续供电会按 Create 原生周期继续尝试。生成的包裹未取走时停止封装。
5. 在正面上部的 Create 数值设置处调整每包装液量：`0` 为自动装包（最多 4000 mB），`1–4000` 为定量。定量不足时等待，不抽走原料。
6. 手持有内容的标准流体容器（例如水桶）右击机器，采样并设置过滤；不消耗手持容器中的流体。空手潜行右击清除过滤。过滤包含流体附加数据；该过滤约束红石自动打包，物流订单按请求的流体身份执行。
7. 像原生打包机一样使用相邻告示牌配置包裹地址。
8. 用蛙港、漏斗等取走包裹，或在机器空闲时手动取走。包裹可进入原生蛙港与锁链输送机运输。
9. 收货端用另一台同种流体打包机贴在目标储罐上。将包裹插入机器，或手持包裹右击机器；不需要拆包模式或额外红石信号。
10. 目标容器正常情况下必须能完整接收一包；空间不足或流体不匹配时不接收。佩戴工程师护目镜可查看机器状态、装液量、过滤和余液信息。

## 流体工厂仪表（0.2 新增）

流体仪表直接继承 Create 的 FactoryPanelBlock、FactoryPanelBlockEntity 和 FactoryPanelBehaviour；配置界面继承 FactoryPanelScreen。四格布局、安装、调频、连接、库存查询、补货时序和在途承诺沿用原生实现。

1. 在货源流体打包机上安装原生存量转信器。用其他存量转信器调频到同一网络，可以将多个货源接入同一物流网络。
2. 手持“流体工厂仪表”右击该存量转信器进行调频。仪表配方：普通工厂仪表、铜锭、流体管道，无序合成。
3. 将仪表安装在普通表面时，它监控所调频网络。手持装有流体的桶、容器或流体包裹点击面板选择流体；不消耗流体。
4. 将已调频仪表安装在**收货端流体打包机**上，则沿用原生补货模式，维持其背后储罐的目标流体存量。
5. 长按使用原生快速数值选择器（mB／B）；点击已设流体的面板打开原生配置界面。新增的“目标 mB”输入框可精确设置 0–100000 mB，点“设定”应用；0 为只监控。
6. 在原生配置界面设置收件地址和在途承诺过期时间。收货端蛙港地址必须与请求地址匹配。
7. 货源收到原生 PackagingRequest 后立即抽取真实流体并生成包裹，超过当前输出位置的包裹进入 Create 原生待发队列。待发流体已从储罐移出，避免重复当作可用库存。
8. 原生在途承诺用于避免重复补货；流体入库正增量会通知原生承诺队列。界面和悬浮显示统一使用 mB。
9. 一格方块仍可放四个流体面板，每个面板各自调频与选择流体。

原生资源接口只认识 ItemStack，因此有一个仅用于身份适配的“流体识别标记”（1 个计数 = 1 mB）。CCD 不把它生成为实际货物、不把它放入包裹、不通过储罐对外暴露可提取的虚拟物品。实际流体包裹仍直接保存 FluidStack。

Create 储罐按多方块控制器去重；第三方跨多个方块实体代理同一存储的容器尚需专门身份适配。原生物品工厂仪表与流体仪表不混放在同一方块中。

实现依据和复用范围见 `docs/create-reuse.md`。本轮按用户要求只编译打包，不启动游戏或测试；不把此前 0.1 的游戏测试结果作为 0.2 实测结论。

## 合装匣（0.3 新增）

原生理包机的订单到齐检查继续使用 Create 的实现。对同一订单中的 CCD 流体与物品，扩展帮助器会整理为“合装匣”：原生 9 个物品槽位，加上独立保存的流体数据，初始合计容量 8000 mB、最多 8 种流体；超出时生成多个匣子。

使用原生库存管理器等入口在同一次订单中请求物品和流体，汇集到合装站库存，再由原生理包机处理。不同订单即使地址相同也不合并。理包机相邻告示牌可设置出站地址，运输继续使用原生蛙港与链条。

创造栏有有效示例匣。当前潜行打开会归还普通物品，并将流体还原为密封流体包裹；自动混合拆包与分流是功能列表下一项。详细实现、数据边界与使用方式见 `docs/composite-case.md`。

## 数据与异常处理

- 每包一种流体，不堆叠，不保存“内罐物品”，保留完整 FluidStack 组件。
- 封装后不能通过物品流体接口直接抽液或追加灌装。潜行打开只提示使用机器，不撕开空包裹。
- 流体包裹从原生随机外观池与默认普通包裹集合中移除；仍通过 `PackageItem` 继承被原生物流识别。
- 普通物品打包机拒收 CCD 流体包裹，避免把它当作空物品包裹消耗。
- 0.3 起原生理包机可以把完整的 CCD 流体／物品订单整理成合装匣。无效、重复或无法识别的混合内容保留在输入库存中。合装匣的自动拆包尚未实现，当前可手动打开为物品和密封流体包裹。
- 模拟填充与真实填充不一致时，未被接收的流体存入恢复数据。机器暂停收发，并尝试回流背后的容器。
- 恢复数据参与存档保存，拆机时转成流体包裹掉落。实际抽取结果与定量预期不符时同样保留、回流。
- 水不会按纸箱规则破坏密封包裹。普通攻击破包时产生可拾取的原内容物品；恢复物品可继续作为包裹运输。火焰、爆炸和虚空等明确销毁路径不提供流体恢复保证。
- 上述保证面向遵守标准流体接口的设备，不声称能修复其他模组在接口内部自行复制或销毁资源的错误。

## 首版边界

- 已实现：自动／定量封装、流体过滤、双向打包拆解、地址、原生收发动画、护目镜信息、基础铜制模型、中文与英文、配方与掉落。
- 已新增：继承工厂仪表的流体仪表、原生物流网络中的 mB 库存摘要、按目标存量自动请求、原生待发队列和在途承诺。
- 0.3 新增：原生理包机合并同订单物品与流体货物，输出可承载多种流体的合装匣；纯物品订单保持原生路径。尚未实现自动混合拆包与分流，以及第三方包裹格式转换。
- 客户端美术是使用原生资源引用和自定义模型组合的功能原型，尚未进行客户端视觉实测。
- 未复制 Repackaged、Create: Fluid 或 FluidLogistics 的实现代码；运行依赖与 API 复用来自 Create、NeoForge。

## 构建与验证

Windows PowerShell（项目目录）：

```powershell
.\build.ps1 -Task build
.\build.ps1 -Task runGameTestServer
.\build.ps1 -Task runClient
```

其他环境也可以使用 Java 21 与 `./gradlew build`、`./gradlew runGameTestServer`。
Windows 脚本只在当前进程使用系统已经配置的网络代理，退出后恢复环境变量，不修改全局设置。

输出位置：`build/libs/ccd-1.21.1-0.3.0-alpha.1.jar`。

游戏测试包括：原生包裹识别与随机池隔离、组件不可变性、完整存档与网络往返、定量不足、属性过滤、拆包容量、执行偏差余液、原生误拆／理包保护、Create 储罐打包拆包往返、接口消失后的余液存档，以及蛙港从 CCD 机器取包并送入原生锁链输送机。

注意：普通 `build` 只编译与打包；游戏测试需要单独运行 `runGameTestServer`。测试日志位于 `run/logs/latest.log`。
