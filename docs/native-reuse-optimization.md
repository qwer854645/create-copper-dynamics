# 第一轮复用优化

## 第三轮：相邻搬液余量归属与手持入口

AdjacentFluidTransfer 的输入／输出共用 transfer：模拟目标接受量有上限、给第三方接口传副本、实际抽出流体类型／数量异常时不直接灌入目标，先返还来源；来源少收或拒绝时明确返回剩余流体。调用端优先恢复万向泵真实 buffer，回滚不重置预算或走输入端口。仍有剩余则在设备处掉落携带真实流体的包裹，沿用水龙头／流体传送器已有恢复惯例；创造源无有限所有权，余量不生成包裹。

上述恢复不保证第三方“声称已接收但实际不存储”、抛异常或任意重入篡改库存时仍能守恒；但正常返回少收、单向来源拒绝回填不再静默丢弃余量。没有增加隐藏持久化恢复罐或更改已有 NBT。

舱口与雾化器现在共享 HandheldFluidExchange.emptyThenFill，内部继续使用 Create FluidHelper 原生灌注优先、抽取回退。舱口的交换样本保护、雾化器过滤槽优先级保留。燃烧室 FluidUtil 路径和铜桶潜行方向语义不强行改写；这一轮只合并行为完全相同的入口。

基础环境和 PnP 3.2.1 环境各 100 项 GameTest 通过，含模拟接收与执行少收、来源拒绝回填、来源接受返还的守恒测试；实际设备缓冲恢复和掉落包裹尚未专门模拟异常接口整链测试。客户端未启动，未重新打包。

## 第二轮：固定相邻能力缓存

水龙头的输入／输出和流体打包机的背部容器改用共享 AdjacentFluidCapability，内部使用 NeoForge BlockCapabilityCache。缓存以关卡、目标坐标和访问面为键；转向时更换缓存，generation 标识使旧缓存监听失效；实体 invalidate 时清理。缺失区块不强制加载，客户端仍采用直接能力查询。模拟、执行和剩余流体恢复流程未改动。

99 项基础 GameTest 通过，新增实际容器拆除、替换和打包机转向后的失效检查。已有水龙头及打包逻辑测试继续通过。没有测量 CPU 耗时，也未扩大到动态桥接器／舱口来源。储液同步、燃料兼容与相邻搬液所有权的说明见下文。

在复用审查后先落实三个可独立验证的改进：

- 缓存泵、万向泵、储罐燃烧室共用 FluidSyncBehaviour，借用 Create 行为生命周期合并储液同步。储液变化立即 setChanged，网络更新通过 dirty 标志延后并限为每 8 tick 一次；最后一次变化仍会被发送。去掉 Liquid Fuel 按刻供燃路径的重复 sendData。原生热量状态变更仍可自行同步，不承诺实体所有网络包都受此上限约束。
- LiquidFuelCompat 使用延迟初始化的方法缓存，避免每次查询重复 Class.forName/getMethod；不缓存燃料数据对象，数据包重载后仍查询最新 LiquidFuels.get 结果。未安装该模组不初始化其反射方法。
- 批量粘接在真实配方 assemble 后检查实际产物是否匹配当前雾化器过滤；不匹配则不加工、不改变输入。普通风扇没有雾化器上下文，因此不受该过滤影响。

没有直接替换为 SmartFluidTankBehaviour 的原因：必须保留旧 Buffer/FuelTank 保存格式及燃烧室暴露 SmartFluidTank 的兼容契约。本轮复用 BlockEntityBehaviour 生命周期，并统一少量节流代码，不宣称已改为原生储罐行为。手持交互、代理、缓存和动画仍未重构。

相邻输送的余量返还需要单独设计。万向泵输出接口拒绝回填，不能把执行时未收下的余量简单交还同一个接口；可选实现是由拥有实际缓存的设备接收返还或保留恢复载荷，还需覆盖存档、拆除和共享预算。为避免本轮引入隐式储液所有权，不改 AdjacentFluidTransfer；原审查标出的风险仍存在。

验证：基础环境与实际安装 Create Liquid Fuel 3.0.0 两种环境均 98 项 GameTest 通过，含新增粘接过滤的拒绝、接受与普通风扇隔离。未测实际包量或 CPU 指标，未进行 PnP 与工业触媒组合回归；这些应随其相关代码改动再验证。本轮未启动客户端或重新打包。
