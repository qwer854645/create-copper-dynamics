# 合装匣与混合订单整理（0.3）

“合装匣 / Composite Case”是 CCD 自己实现的复合包裹，不是三个流体附属中任一载体的代码移植。
本轮只阅读 Create `6.0.10-280` Maven 源码及 CCD 自有代码，未读取 Repackaged、Create: Fluid、FluidLogistics 的实现代码。

## Create 原生机制与扩展位置

参考源码：

- `PackageRepackageHelper.addPackageFragment`：收集原生订单分片；内部的 `isOrderComplete` 判定链路、分片、末链和末片是否完整。
- `PackageRepackageHelper.repack`：原生物品摘要和按配方整理路径。
- `RepackagerBlockEntity.attemptToRepackage`：扫描背后库存、等待完整订单、重组、消耗原包裹并进入输出队列。
- `PackageItem`：物品内容、地址、订单上下文、包裹身份及实体运输。

CCD 的 `CompositeRepackageHelper extends PackageRepackageHelper` 直接调用父类的到齐检查。
原生理包机通过一个构造尾部 Mixin 换用这个帮助器；扫描、接收、红石、动画、队列和存档仍由原生机器负责。
纯物品订单调用父类 `repack`，不重写其配方整理算法。

只有包含 CCD 流体包裹或合装匣的完整订单，才进入自有的物品与流体合装逻辑。
在允许原生机器消耗输入之前，先构造并验证所有输出匣；有无法处理的内容时继续保留输入。

## 载体

- 继承 `PackageItem`，单个物品，不堆叠。
- 物品沿用原生 `PACKAGE_CONTENTS`，9 个槽位，保留物品组件和原生堆叠上限。
- 流体直接保存在 `ccd:composite_fluids` 数据组件中，保留每种流体的完整属性；不是内装流体罐或识别标记物品。
- 初始容量：所有流体合计 8000 mB，最多 8 种具有不同身份／附加数据的流体。
- 超限时输出多个合装匣，不截断内容。
- 可以承载物品与流体、多个流体，或在容量分割后只承载其中一种货物。
- 沿用原生地址、订单编号和上下文。多匣输出使用连续的原生分片编号，末匣标记结束，便于再次理包。
- 只有在最后一个输出匣上附带完整订单上下文。混合配方的自动执行／按配方批次分箱并未在本项中实现。
- 外观为自建 JSON 模型，引用 Minecraft／Create 材质资源。未复制其他流体附属的贴图或模型。

## 使用

1. 使用原生库存管理器等入口，在**同一次原生订单**中请求物品与流体识别项；识别项数量代表 mB。
2. 将该订单各货源输出的包裹送到同一合装站的箱子或其他原生理包机可读取的库存。
3. 用原生理包机处理这个库存，并通过原生红石方式启动。
4. 等待原生订单分片到齐后，机器输出合装匣。给理包机配置相邻告示牌，可把生成匣子的地址改为最终目的地；地址读取调用原生方法。
5. 使用原生蛙港、锁链输送机及其他包裹运输路径运送。

**同地址不代表同订单。** 两次分别请求出来的物品／流体包裹不会自动被认作一单；没有订单信息的包裹沿用原生原样转交流程。

创造栏提供一个装有铁锭和 1000 mB 水的有效示例匣，方便查看载体。

## 当前拆解能力

本项对应功能列表中的“混合订单整理”。自动“混合货物拆包与分流”是下一项，尚未实现。

当前可潜行使用手动打开：普通物品归还背包，流体拆成不超过 4000 mB 的密封流体包裹。背包溢出按原生物品归还方式掉落，不把流体放置到世界中。
手动打开会结束原包裹的地址／订单运输关系，与原生手动拆包的含义一致。
普通物品打包机与单流体打包机拒收整个合装匣，避免只取走一部分内容后丢弃其余货物。

## 输入边界

- 同订单地址不一致、分片编号重复、数据无效、嵌套包裹、物理识别标记，以及 CCD 无法理解的第三方包裹与 CCD 流体混合时，不进行重组。
- 纯物品／第三方原有订单保持原生路径；本轮没有通用解释其他模组私有包裹数据。
- 对含 CCD 货物的订单，会核对原生理包机准备消费的同订单输入数量，避免未参与整理的额外包裹被原生批量移除。
- 普通攻击、含水环境与明确销毁路径沿用 CCD 密封包裹的规则，整个匣子的内容作为整体处理。

本轮仅编译和打包，没有运行游戏测试或客户端视觉检查；不以旧版本测试结果代表 0.3 已实测。
